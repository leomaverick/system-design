1. Scalability

Vertical scaling (scale up): increase resources such as CPU or RAM on an existing machine. Horizontal scaling (scale out): add more service instances and distribute traffic between them.

Example: when marketplace checkout traffic increases, add Checkout Service replicas behind a load balancer. Application scaling alone does not guarantee overall scalability: the database or an external dependency may still become a bottleneck.

↑ Contents

2. Load Balancing

A load balancer distributes incoming traffic across backend instances to help with capacity and availability. It can be software such as NGINX or HAProxy, or a managed cloud service. In Kubernetes, Services and Ingress/Gateway resources can participate in routing; an external load balancer is not necessarily a Kubernetes Pod.

Health checks prevent new traffic from being sent to unhealthy backends. Load balancing does not remove every single point of failure: the balancer itself and shared dependencies must also be highly available.

3. Load-Balancing Algorithms

  • Round Robin: cycle through healthy servers in sequence. It distributes request counts rather than equal amounts of work.
  • Weighted Round Robin: allocate more requests to servers with greater assigned weights, useful when instance capacities differ.
  • Least Connections: prefer servers with fewer active connections, often helpful when connection durations vary.
  • Weighted Least Connections: consider both assigned weights and active connections when selecting a backend.

Trade-off: active connections are not a direct measure of CPU load, especially with multiplexed protocols. Validate choices using throughput, request latency, CPU saturation, and error rates.

Example NGINX configuration:

upstream checkout_service {
    least_conn;
    server checkout-a:8080 weight=4;
    server checkout-b:8080 weight=2;
}

4. Stateless vs. Stateful Services

Stateless: an instance does not depend on client-specific session state retained locally between requests. It may still use temporary memory, connection pools, external databases, and caches.

Stateful: the system maintains meaningful state across operations, whether in memory, on disk, or in persistent storage. A database is a classic example.

Why stateless scales well: any healthy replica can handle a subsequent request. Local-only sessions may require sticky sessions and complicate recovery when an instance crashes.

5. JWT, Redis & Shopping Carts

JWT authentication can be stateless: each service instance validates the token's signature, issuer, audience, and expiration without relying on a local authentication session. But shopping cart data is business state, not authentication state, and must remain accessible across requests.

Shared storage allows multiple stateless instances to continue the same shopping experience. Redis can support caching, ephemeral state, and rate limiting, while a durable database may hold the authoritative shopping cart data. Early token revocation can require shared revocation state.

6. Redis Failure & Fallback

One practical design keeps a durable database as the source of truth and uses Redis as a cache. If Redis becomes unavailable, the service can fall back to the database under controlled conditions, with timeouts, circuit breakers, capacity monitoring, and load protection.

Redis replication and automatic failover can reduce downtime. Avoid independent, uncoordinated dual writes to Redis and the database; handle cache invalidation and stale reads explicitly.

7. High Availability

High availability means keeping a service accessible and operational with minimal downtime. It is not simply the number of instances deployed. Redundancy, health checks, automated failover, and the elimination of single points of failure are common techniques.

Example: one of three Checkout Service instances goes offline; healthy instances continue handling traffic.

8. Fault Tolerance

Fault tolerance is the ability to continue performing essential functions despite component failures, potentially with controlled degradation. It overlaps with high availability, but describes how the system behaves under failure rather than only how much downtime it experiences.

Example: Redis fails, but checkout continues using the durable database with protective limits.

9. Kubernetes Health Checks & Auto Healing

Kubernetes uses probes to assess containers and determine whether they can receive traffic or require a restart.

  • Readiness probe: indicates whether a Pod is ready to serve traffic. When readiness fails, Kubernetes marks the Pod not ready and removes it from the ready endpoints used by Services, so new traffic is not routed to it.
  • Liveness probe: checks whether a container should be restarted. When liveness fails repeatedly beyond the configured threshold, kubelet restarts the container.
  • Startup probe (when configured): gives slow-starting applications time to initialize before liveness/readiness checks take effect.

Important nuance: a liveness failure is not itself the mechanism for traffic removal. Readiness is responsible for endpoint eligibility. Avoid treating a temporary dependency failure as a reason to endlessly restart otherwise healthy application containers.

Example: a Checkout Pod is running but cannot reach a required database. A well-designed readiness check can mark it unready and remove it from normal service routing. Whether its container should restart is a separate liveness decision.

10. Kubernetes Auto Scaling

The Horizontal Pod Autoscaler (HPA) adjusts replica counts based on resource metrics (such as CPU or memory utilization) or configured custom/external metrics. It does not simply react to a load balancer detecting a traffic spike. Define realistic CPU/memory requests, appropriate limits, minimum and maximum replicas, and scaling behavior. Readiness probes ensure new Pods receive traffic only when ready; a Cluster Autoscaler or node provisioning mechanism may be needed if the cluster lacks capacity for new Pods.

Interview example: “I would configure HPA with CPU or application-level metrics, right-size resource requests and limits, and use readiness checks. I'd verify node capacity and monitor latency, saturation, and errors to avoid scaling the application while leaving a database bottleneck.”

11. Resilience Patterns

Goal: contain failures in dependencies so slow or unhealthy components do not exhaust resources or cause cascading failures. Patterns work together, rather than substituting for one another.

11.1 Timeouts

Set a bounded wait for outbound operations so stalled dependencies do not occupy resources indefinitely. Handle timeout results explicitly. A client timeout does not prove the remote operation failed or was cancelled, especially for payments.

Example: Checkout stops waiting for Payment after its configured deadline and returns a safe result; it does not assume the charge was unsuccessful.

11.2 Retry with Exponential Backoff and Jitter

Retry transient failures only when it is safe, using increasing delays (for example, 1, 2, and 4 seconds), random jitter, retry limits, and an overall deadline. Avoid retry storms. Payment retries require idempotency keys and, when needed, status reconciliation because the first attempt might have succeeded.

11.3 Circuit Breaker

A circuit breaker prevents repeated calls to an unhealthy dependency. Closed permits calls and monitors failures; Open fails fast without calling the dependency; Half-Open permits limited probe calls to evaluate recovery. Configure thresholds and fallback behavior carefully.

11.4 Bulkhead

Isolate concurrency or execution resources per dependency. For example, Checkout may allow at most 30 concurrent Payment calls and 30 Inventory calls. If Payment becomes slow and saturates its allocation, it cannot consume Inventory's allocated slots. A semaphore bulkhead limits concurrency; a thread-pool bulkhead additionally provides separate execution pools/queues. Shared infrastructure limits still matter.

Where: protect outgoing calls inside the Checkout Service; downstream services can also implement their own isolation.

11.5 Graceful Degradation

Keep safe, valuable functionality working when a noncritical dependency fails. If Recommendations is down, omit recommendations but keep browsing and checkout functional. If Payment is unavailable, retain the cart and offer a later retry; never mark an unpaid order as paid.

Interview Question

Q: Payment has high latency and intermittent failures. How do you protect Checkout?

“I'd use bounded timeouts, selective retries with exponential backoff and jitter, and idempotency for payment operations. I'd add a circuit breaker to fail fast when Payment is unhealthy, bulkheads to protect resources needed by Inventory and other dependencies, and graceful degradation that preserves the cart without falsely confirming payment. I'd monitor latency, error rates, and traces.”

12. Capacity Planning

Estimate expected peak requests per second, then load-test to measure sustainable per-instance throughput within latency and error-rate targets. Approximate baseline instance count as peak RPS ÷ safe RPS per instance, rounded up. Add headroom for failures, deploys, and spikes. Review database connections, caching, queue depth, downstream rate limits, and cluster node capacity.

Example: 10,000 RPS ÷ 500 safe RPS per instance = 20 instances minimum under these assumptions, before headroom.

Measure: throughput, CPU/memory saturation, error rate, P95 and P99 latency, and service-level objectives. Auto scaling cannot compensate for a saturated database.

Interview Question

Q: How would you size a checkout platform for 10,000 RPS?

“I'd estimate peak traffic and load-test sustainable throughput under P95/P99 latency targets. If one replica safely handles 500 RPS, I'd start from 20 replicas, then add capacity headroom and configure HPA. I'd also validate database capacity, queueing, and downstream limits, since app replicas are only one part of the system.”

13. Interview Answers (English)

Scalability

“Scalability is the ability to handle increasing workloads while maintaining acceptable performance. I would consider horizontal or vertical scaling, but also measure bottlenecks across databases and downstream dependencies.”

Load Balancing

“Weighted Round Robin accounts for differences in backend capacity, while Weighted Least Connections also considers active connections. I would validate the strategy against real production metrics.”

Stateless Services

“A stateless service doesn't rely on locally retained client-specific session state between requests, so any healthy instance can handle subsequent requests using request context and shared storage where needed.”

Redis Resilience

“I'd use a durable database as the source of truth and Redis as a cache. If Redis goes down, I'd use controlled fallback and monitor database capacity while Redis replication and failover support recovery.”

High Availability vs. Fault Tolerance

“High availability focuses on minimizing downtime, while fault tolerance is the ability to continue functioning despite component failures. Redundancy and failover can contribute to both.”

Readiness vs. Liveness

“Kubelet runs readiness and liveness probes. If readiness fails, the Pod is marked unready and excluded from ready Service endpoints, preventing new traffic. If liveness fails, the container is restarted; traffic resumes only once the Pod is ready again.”

Auto Scaling

“HPA scales replicas based on resource or configured custom metrics. I combine it with resource requests, readiness probes, node capacity planning, and performance monitoring.”

Resilience Patterns

“I combine timeouts, safe retries with backoff and jitter, circuit breakers, bulkheads, and graceful degradation to contain dependency failures. For payments, I also protect against duplicate operations with idempotency.”

Capacity Planning

“I determine peak load, load-test safe throughput per replica under latency targets, size for headroom, and validate databases and other shared bottlenecks.”
