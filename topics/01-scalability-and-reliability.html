Scalability, Load Balancing & Reliability

Resumo dos conceitos que estudamos com exemplos do Checkout Service de um marketplace.

1. Scalability

Vertical scaling: aumenta recursos de uma instância, como CPU ou RAM. Horizontal scaling: adiciona instâncias para distribuir a demanda. Exemplo: três réplicas de Checkout Service atrás de um balanceador.

↑ Índice

2. Load Balancing

Um load balancer distribui o tráfego entre réplicas de backend. Pode ser NGINX, HAProxy ou serviço de nuvem. Em Kubernetes, Services e Ingress/Gateway integram o roteamento, mas o balanceador externo não precisa ser um pod.

Health checks ajudam a retirar instâncias indisponíveis do tráfego.

↑ Índice

3. Algoritmos de distribuição

  • Round Robin: alterna servidores, adequado para capacidades e demandas semelhantes.
  • Weighted Round Robin: usa pesos para dividir requisições de acordo com a capacidade relativa, mas não acompanha a carga instantânea.
  • Least Connections: tende a escolher a instância com menos conexões ativas, podendo ajudar com operações de duração variável.
  • Weighted Least Connections: combina quantidade de conexões e peso; uma aproximação é comparar conexões ativas divididas pelo peso.

Importante: conexões não medem diretamente CPU ou custo de processamento, especialmente quando uma conexão carrega várias requisições. Validar com latência, throughput, erros e uso de recursos.

upstream checkout_service {
    least_conn;
    server checkout-a:8080 weight=4;
    server checkout-b:8080 weight=2;
}

4. Stateless versus Stateful

Stateless não significa ausência de memória: significa que a instância não depende de estado de sessão armazenado localmente entre requisições. Cada réplica consegue atender a próxima requisição usando os dados enviados e recursos compartilhados.

Stateful mantém estado entre operações, em memória, disco ou armazenamento persistente. Sessões locais podem exigir sticky sessions e criar dificuldades se a instância falhar.

5. JWT, Redis e carrinhos

JWT permite autenticação stateless com validação da assinatura, issuer, audience e expiração em cada réplica. Entretanto, o carrinho de compras é estado de negócio, diferente da sessão de autenticação. As informações do carrinho precisam estar disponíveis às várias instâncias.

Redis pode oferecer acesso rápido, cache, controle de rate limits e estado temporário. O banco durável pode ser a fonte de verdade. Mecanismos de revogação antecipada de JWT podem precisar de um registro compartilhado.

↑ Índice

6. Falhas do Redis e fallback

Para reduzir perda de carrinhos, grave dados no banco autoritativo e use Redis como cache. Se Redis falhar, o serviço pode acessar o banco diretamente, com fallback controlado, timeouts, circuit breakers e observabilidade para não sobrecarregar o banco.

Replicação e failover automático reduzem interrupções. Evite dual writes independentes em Redis e banco, pois podem gerar inconsistência; trate invalidação e atualização do cache.

↑ Índice

7. High Availability

Alta disponibilidade significa manter o serviço acessível com o mínimo de downtime — não simplesmente ter o máximo de instâncias. Requer redundância adequada, health checks, failover e atenção a pontos únicos de falha, inclusive no banco.

Exemplo: uma das três instâncias cai e o balanceador redireciona novas requisições às outras duas.

↑ Índice

8. Fault Tolerance

Tolerância a falhas é a capacidade de continuar executando funções essenciais apesar de falhas de componentes, às vezes com degradação. Exemplo: Redis falha, mas a aplicação continua utilizando o banco principal. Alta disponibilidade é um objetivo de continuidade; tolerância a falhas é uma propriedade que pode ajudar a alcançá-lo.

9. English interview answers

Load balancing

“Weighted Round Robin accounts for different backend capacities, but not real-time workload. For requests with varying durations, I'd consider Weighted Least Connections and validate it using production metrics.”

Stateless vs Stateful

“A stateless service doesn't retain client-specific session state locally between requests, so any healthy instance can handle the next request using shared storage when necessary.”

Redis failure

“I'd use a durable database as the source of truth and Redis as a cache. If Redis becomes unavailable, I'd use a controlled fallback while monitoring database load and enabling Redis replication and failover.”

High availability vs fault tolerance

“High availability focuses on minimizing downtime. Fault tolerance means the system can continue functioning despite component failures. Redundancy and automatic failover can contribute to both.”
